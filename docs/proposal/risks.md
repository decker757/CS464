# §4.3 Technical risks — draft

## Body version

The nine rows that fit the page budget, with the guideline's technical-debt bullet as the paragraph under the full table. L and I are likelihood and impact.

| Risk | L | I | Mitigation | Status |
|---|---|---|---|---|
| No performance numbers; each trade makes two HTTP calls and queues on its book lock (#20, ADR 0017, 0022, 0024, 0026) | H | H | Load test at 50 users against this deployment, recording p95 | Planned |
| No staging: a push to `main` reaches users unrehearsed (ADR 0026) | H | M | CI on `dev`, advisory; stack test on a runner; a server that does not start goes back | Not built |

| 1 | **No performance numbers.** The scalability claims are argued but not measured. Every trade makes two synchronous HTTP calls (auth and market_service), queues on its market's book-row lock, and does extra work under that lock for each resting order it fills. | High (certain) | High | A load test against the trade endpoint, recording p95 latency at 50 concurrent users, against this deployment. #440 has shown two replicas of every service working behind nginx, including a quote from one ledger replica honoured by the other. | Planned (#20 open). | 2 | **No staging environment.** Every push to `main` goes straight to production, and the deploy runs no suite of its own. #19's staging criterion is unmet. | High (certain) | Medium | CI normally runs on `dev` before a promotion, but it is advisory and nothing requires it green. `ci-deploy.yml` runs the production stack and `release.sh`'s failure paths on a runner. | 4 | **The database's connection ceiling.** The 2 GB plan allows about 47 connections, shared by every replica of every service. Two servers use 40 at full overflow, which leaves room for the migrate steps, run one after another. A third server would pass the ceiling, and the errors would look like a bug in a service rather than a sizing problem. | Medium | High | Each service's pool is a setting, sized in `deploy/production/compose.yml`. | 5 | **`/lb-health` asks only the ledger.** A server whose auth or market service is unhealthy but still running keeps getting traffic, and nothing restarts it, because Docker only restarts a container that exits. No service's `/health` reads a database or calls another service. | Medium | High | Every service's health check must pass before a deploy brings a server back, and the deploy's public check asks the same paths, so both show only that each process answers. #599 should check every service behind `/lb-health`, or alert on each. | Accepted until #599. | ADR 0026; #599 |
| 6 | **A migration stays applied when its release is sent back.** A migration that breaks the release before it breaks the rollback too. Reverting such a release on `main` also fails, because the deploy migrates first and Alembic refuses a database newer than the code. | Medium | High | Add a column first and drop the old one a release later. `docs/deployment.md` and `CLAUDE.md` say so where people will read it. Nothing tests it. To undo a release with a migration, fix forward, or go back by hand on each server. | Accepted. A rule, not a check. | ADR 0026 |
| 7 | **No login rate limit, on a public site.** `/auth/login` and `/auth/register` accept as many attempts as anyone sends. Argon2 is slow on purpose and runs inside auth's async handler, on the one worker's event loop, on a 1 vCPU server shared with four other services. A flood can stall auth, the ledger's per-trade call to it then times out at 5 seconds, and trades answer `503` while `/lb-health` stays green. Read from the code, not measured. | Medium | High | Passwords are hashed with Argon2id, which slows each guess. #600 limits per account and per address, across replicas. | Not built (#600 open). | ADR 0026; #600 |
| 8 | **A live access token cannot be revoked.** Logout, demotion and suspension each take up to 15 minutes to take effect, and market_service never learns of a suspension. | Medium | Medium | The access token lives 15 minutes. The ledger asks auth on every trade, so a suspended trader stops trading at once. Auth reads the live user row. A `jti` denylist is the named fix. | Accepted. | ADR 0002 *Cookies for the browser, bearer tokens for services*; ADR 0003 *A separate market service, and admin authority carried in the token*; ADR 0007 *A flat admin tier, and role changes audited rather than approved*; ADR 0022 |
| 9 | **Trading depends on three services.** Every trade calls auth and market_service, so if either is down on a server, trading through that server stops. | Medium | Medium | Failing closed (`503`) is the right direction. Calls time out after 5 seconds. Two servers mean one server's failure need not stop trading, but only if the load balancer takes it out: see row 5. | Accepted. | ADR 0017; ADR 0022; ADR 0026 |
| 10 | **One Postgres, with no standby.** All four database services share one node, so it is the single point of failure. | Low | High | DigitalOcean's daily backups cover data loss, though the repository records no restore having been tried. A standby node would cover downtime, at double the database's cost, and is not bought. | Accepted. | ADR 0026; ADR 0001 *Self-host authentication instead of using a managed provider* ("The data tier is the real single point of failure") |
| 11 | **The cookie needs one registrable domain.** The `SameSite=Lax` session cookie is not sent on cross-site requests, and it is the WebSocket's only browser credential. Staging at `staging.<domain>` would receive production sessions. | Low | High | Production serves everything under one domain and sets `COOKIE_DOMAIN` to it. Staging needs a registrable domain of its own. Move to `SameSite=None` only after adding CSRF tokens. | Met in production. The setting still accepts `none` with no CSRF defence. | ADR 0002; ADR 0010 *A relay that owns nothing, and a bus that is not the database*; ADR 0026 |
| 12 | **The JWT secret is shared and HS256.** All five services hold `JWT_SECRET`, so any service that can verify a token can also mint one, including an admin's. | Low | High | Verifiers have no encode path, and a test fails if one is added. Terraform generates the secret, and it lives in the GitHub `production` environment and each server's `app.env`. RS256 or EdDSA is the named upgrade. | Accepted. | ADR 0002; ADR 0003; ADR 0026 |
| 13 | **One copy of the Terraform state.** `terraform.tfstate` holds every production secret and the record of what exists. It is on the machine that ran `apply`, gitignored, with no remote backend. Lost, Terraform cannot manage what it made until each part is imported again. Leaked, every secret must be rotated. | Low | High | `docs/deployment.md` says to keep it and not share it. The running site does not read it, and the deploy reads its secrets from the GitHub `production` environment. A remote backend is the upgrade. | Not built. | `docs/deployment.md`; `infra/terraform/versions.tf`; ADR 0026 chooses Terraform and does not say where its state lives |
| 14 | **SSH is open to the internet, and the deploy user is root in all but name.** Port 22 admits any address, because GitHub's runners have no fixed one. The `deploy` user is in the `docker` group, which is equivalent to root on that server, and its key is in the GitHub `production` environment. | Low | High | Keys only, no root login, `deploy` the only user allowed. The environment accepts `main` only, and the deploy checks host keys that Terraform generates. | Accepted. | ADR 0026; `infra/terraform/servers.tf`; `infra/terraform/cloud-init.yaml.tftpl` |
| 15 | **The migrate step must run once per deploy.** It takes no lock, so two copies at once would fail. | Low | Medium | `release.sh` runs it once, from the first server, before any server rolls, and stops the deploy if it fails. The workflow runs one deploy at a time. In production a step runs only when named, behind a Compose profile. Locally, Compose starts each app only after its step exits 0, and tests fail if the scale override gives a step more than one replica. | Built. | ADR 0020 *Migrations by Alembic, per service, run as a one-off step*; ADR 0026; `docs/horizontal-scaling.md` |
| 16 | **Audit atomicity holds only while the services share one database.** An admin action and its audit entry commit together. A service moved to its own database would need an outbox and a relay. | Low | Medium | Every write goes through one function (`shared/audit.py`), and an outbox is the named upgrade. This rules out one database per service. | Accepted. | ADR 0006 *One shared audit log, written in the acting service's transaction* |

| 18 | **A gap between the commit and the price publish.** A crash or a bus outage after a trade commits leaves screens showing an old price. Nothing is replayed from the bus. | Low | Low | A failed publish is logged and never fails the trade. Every frame carries a `state_version`. A client that reconnects reads a snapshot. The 30-second poll covers only markets the socket is not carrying, so a lost publish on a connected socket stays stale until the next frame. | Accepted. | ADR 0010 |

**Managing technical debt.** An ADR records each accepted risk with the condition that would reverse it. DECISIONS.md holds the smaller decisions, and code comments cite them by number. Guard tests pin the risky boundaries. For example, `test_the_audit_grant_is_exactly_insert` fails if the audit grant is widened, and the scale-override tests fail if a migrate step gains a replica. A risk above becomes work when its trigger fires, not before.
