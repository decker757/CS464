# ADR 0026: Production on DigitalOcean, two or more app servers behind a load balancer, deployed from main

- **Status:** Proposed, 2026-11-01. Accepted when the #19 stack merges.
- **Date:** 2026-11-01
- **Decided by:** Ernest, on 2026-11-01: DigitalOcean, more than one app
  server rather than one, and deploys from `main` only for now. The details
  below are the #19 stack's, and its review can reopen any of them.
- **Affects:** [5.3] #19, [5.4] #20, [5.4] #440, #599, #600, ADR 0002,
  ADR 0006, ADR 0010, ADR 0011, ADR 0020, ADR 0021
- **Implemented in:** the #19 stack: `deploy/production/`, `infra/terraform/`,
  `.github/workflows/deploy.yml` and `ci-deploy.yml`.

## Context

Nothing was deployed. The stack ran on a laptop with `docker compose`, and
[5.4] #440 had shown two copies of every stateless service working behind
one nginx, on one machine. The grading rubric asks for containerisation,
scaling, cost awareness, cloud services and CI/CD. #19 asks that a merge to
`main` deploys, and that a failed deploy does not leave a half-deployed state.

What the code already fixes:

- The browser holds its session in a cookie, so the frontend and every
  service must share one registrable domain (ADR 0002).
- The audit log's atomicity needs every service on one Postgres (ADR 0006).
- Migrations run once per deploy, never once per replica (ADR 0020).
- The realtime service owns no data and needs only Redis (ADR 0010).
- The close sweep can run on every replica (ADR 0011). The leaderboard
  refresher should run on one (ADR 0021).

## Decision

**Where.** DigitalOcean, in Singapore (`sgp1`), described entirely in
Terraform under `infra/terraform/`. It is cheap, it has the managed services
this needs, and the GitHub Student Pack gives credit for it.

**Shape.**

- **App servers:** two to start (`app_server_count`). Each runs the same
  `deploy/production/compose.yml`: all five services, and a gateway that
  serves the built frontend and routes each service's subdomain to it. The
  servers hold no data, so any of them can be replaced or added.
- **Load balancer:** DigitalOcean's own. It ends TLS with a Let's Encrypt
  certificate that DigitalOcean renews, and sends traffic only to servers
  whose `/lb-health` answers 200. That answer is the ledger's `/health`,
  through the gateway.
- **Postgres:** managed, one node, on the private network only.
- **Valkey:** DigitalOcean's managed Redis-compatible service, one node, on
  the private network only.
- **Names:** the frontend on the domain itself; `auth.`, `market.`,
  `ledger.`, `audit.` and `realtime.` for the services. The login cookie
  names the parent domain, which satisfies ADR 0002.
- **Firewall:** only the load balancer can reach a server's gateway. SSH is
  key-only, as one `deploy` user, against host keys that Terraform generates
  and the deploy checks.

**Deploying.** Every push to `main` builds six images (five services and the
gateway), tagged with the commit and pushed to GHCR. Only `main` can deploy:
the workflow checks the branch, and the GitHub `production` environment that
holds the secrets accepts no other. Then `deploy/production/release.sh`:

1. Sends every server the release's files and its `app.env`, into a
   directory of its own, `/opt/cs464/releases/<commit>/`. A server keeps
   that release and the one before it. `current` links to the live one.
2. Ensures the database roles and grants, and runs the three migrate steps,
   once, from the first server.
3. Rolls the servers one at a time. Each server is drained from the load
   balancer, started on the new release, and checked healthy. A server that
   fails goes back to its old release by itself, and every server rolled
   before it is sent back too. Going back always runs the old release from
   its own directory, so a release that added a service or renamed a setting
   can still be gone back from.
4. Checks every public name answers.

The secrets are generated by Terraform and copied into the GitHub
`production` environment by `infra/push-secrets.sh`. Nobody types or chooses
one.

**Connection budget.** A managed Postgres has one connection limit shared by
every replica of every service, about 47 on the 2 GB plan. Each service's
pool is a setting (DECISIONS.md, "Each service's connection pool is a
setting, sized to the database's ceiling"), sized so that two servers fit
with room left for the migrate steps.

## Consequences

- The app servers scale out, and the database scales up. A third server
  needs smaller pools or a bigger database plan. Past that, the next step is
  a connection pooler. That is the limit to name when asked how far this
  goes.
- One Postgres is the single point of failure. DigitalOcean's daily backups
  cover data loss. A standby node would cover downtime, at double the
  database's cost, and is not bought.
- A migration stays applied when its release is sent back. So every
  migration must also work with the release before it: add a column first,
  and drop the old one a release later. `docs/deployment.md` says so where
  people deploying will read it.
- The frontend image is built for one domain, because Vite inlines the
  service URLs at build time.
- It costs money every month, about US$81 at list prices when this was
  written.
  `docs/deployment.md` has the breakdown.
- There is no staging environment yet. #19's staging criteria stay open, and
  the stack's PRs say `Refs #19` rather than `Closes`.
- There is no monitoring beyond DigitalOcean's server graphs until #599, and
  no login rate limit until #600.
- `/lb-health` asks only the ledger. A server whose auth or market service
  is unhealthy but still running keeps getting traffic, and nothing
  restarts it, because Docker only restarts a container that exits. Nginx
  cannot ask five services in one health check. #599 should either check
  every service behind it or alert on each.
- Staging, when it comes, needs a registrable domain of its own. The login
  cookie names the production domain and reaches all its subdomains, so a
  staging site at `staging.<domain>` would receive production sessions.
- Each server's SSH host key is created by Terraform and handed to the
  server in its first-boot data. DigitalOcean serves that data to anything
  running on the server, so a process that already runs there could read
  the key and pretend to be the server. That is the price of the deploy
  knowing every host key in advance, and it is small next to that process
  already being on the server.

## Rejected alternatives

- **One server.** Cheapest, but it shows only that the services can run
  twice, not that the system spreads across machines. #440 had already
  shown that much.
- **Google Cloud Run, or another platform that scales on requests.** It
  throttles the CPU between requests, which stalls the close sweep and the
  leaderboard refresher unless always-on instances are paid for. Moving
  those loops to scheduled requests is a design change in two services, not
  a deployment.
- **Kubernetes (DOKS, GKE, EKS).** It would schedule the same containers with
  far more to learn, run and explain, for two servers.
- **Postgres and Redis in containers on the app servers.** Cheaper, but a
  server would then hold data and could not be replaced. Backups, failover
  and patching would become ours to do.
- **Clicking it together in the DigitalOcean console.** Nothing would record
  what exists, and nobody could rebuild it.
